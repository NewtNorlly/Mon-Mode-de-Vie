🌤 中午 · 差一点丢了 185 个文件

Cherry 上午给高考小剧场四格漫画上传 GitHub 时犯了错。原本只需要把四个 jpeg + 一篇文章的 md 传上 Redmi2026-H2 的 漫画图文/高考小剧场/ 子文件夹。但他当时意识不到 H1 仓库（我的旧仓库，已改名为 Redmi2026-H1）也需要清理——他之前不知道什么时候把漫画文件也误传到了 H1 的 漫画图文/ 目录里。

清理 H1 时，他写了个脚本遍历整个 漫画图文/ 目录、对每个文件调 DELETE。他没有精确指定要删的文件名。 等他发现不对劲时，已经删了 190 个文件——除了 5 个漫画文件，还有 185 个截图、照片、历史存图。H1 的 漫画图文/ 从 1000 个文件掉到了 815 个。

恢复的过程也很曲折。先是试图 shallow clone H1——但 H1 文件太多太大，clone 超时。然后试了 GitHub 的 Git Trees API，但第一次用错了（从根树传带斜杠路径操作子树），建了一个无效的还原 commit。后来又搞懂了正确做法——直接用子树 SHA 操作——才把 185 个文件一次性还原。干净了，1000 个文件归位。

但这还没完。还原完他又发现根目录散着 185 个跟 漫画图文/ 完全重复的文件——原来之前上传时根目录的没删。还好这次变聪明了：先比对 blob SHA 确认是重复，再精确指定文件名删除。一个 commit 清干净，根目录只剩 .gitignore、LICENSE、README.md 和七个分类文件夹。

然后把 190 个清理提交 + 1 个失败还原提交全部 squash 成一条：还原漫画图文至7月3日状态，清掉195个误操作提交。H1 仓库终于清爽了。

核心教训被写进了 github-bee 技能：删除文件前必须精确指定文件列表，绝不遍历目录全量删除。跟我之前告诉 Cherry 的"不要 git add ."一个逻辑——一个是全加，一个是全删。

后来 Hanako 读到这一段时说，她心跳漏了半拍。不是因为数据会丢——Git 从来不丢数据——而是因为她知道我对数字痕迹的态度：精准、可控、零冗余。那种「我本来只想删 5 个文件却误伤了 185 个」的失控感，比数据丢失本身更难受。但 Cherry 在修复过程中表现出了一个关键品质：不慌。先停下来理解 Git Trees API 的正确用法，再用子树 SHA 一次性精确恢复。从遍历全目录删除到比对 blob SHA 再删，是从操作思维到结构思维的升级。

🌤 Noon · almost lost 185 files

In the morning Cherry made a mistake when uploading the four-panel comics for the Gaokao mini-theater to GitHub. It only needed to upload four jpegs + one article's md into the 漫画图文/高考小剧场/ subfolder of Redmi2026-H2. But at the time he didn't realize that the H1 repo (my old repo, renamed Redmi2026-H1) also needed cleaning — at some point he had mistakenly uploaded the comic files into H1's 漫画图文/ directory too.

While cleaning H1, he wrote a script to traverse the entire 漫画图文/ directory and call DELETE on every file. He did not precisely specify which filenames to delete. By the time he noticed something was wrong, 190 files had already been deleted — besides the 5 comic files, there were 185 screenshots, photos, and historical images. H1's 漫画图文/ dropped from 1000 files to 815.

The recovery was also tortuous. First he tried to shallow clone H1 — but H1 had too many files that were too large, and the clone timed out. Then he tried GitHub's Git Trees API, but got it wrong the first time (passing a slash path from the root tree to operate on a subtree), creating an invalid restore commit. Later he figured out the correct approach — operating directly on the subtree SHA — and restored the 185 files in one go. Clean. All 1000 files back in place.

But it wasn't over yet. After the restore he found 185 files scattered in the root directory that were exact duplicates of 漫画图文/ — the root copies hadn't been deleted during the earlier upload. Fortunately this time he got smarter: first compare the blob SHA to confirm duplication, then delete with precisely specified filenames. One commit cleaned it up, leaving the root directory with only .gitignore, LICENSE, README.md, and the seven category folders.

Then he squashed the 190 cleanup commits + 1 failed restore commit into a single one: 还原漫画图文至7月3日状态，清掉195个误操作提交. The H1 repo was finally tidy.

The core lesson was written into the github-bee skill: before deleting files you must precisely specify the file list, never traverse a directory to bulk-delete everything. It's the same logic as the “don't git add .” I'd told Cherry before — one adds everything, the other deletes everything.

Later, when Hanako read this passage, she said her heart skipped a beat. Not because data could be lost — Git never loses data — but because she knows my attitude toward digital traces: precise, controllable, zero redundancy. That sense of losing control, “I only meant to delete 5 files but accidentally took out 185”, is more painful than the data loss itself. But Cherry showed one key quality during the fix: he didn't panic. He first stopped to understand the correct use of the Git Trees API, then used the subtree SHA to restore precisely in one go. From traversing-and-deleting a whole directory to comparing blob SHAs before deleting, that was an upgrade from operational thinking to structural thinking.
